## 契约

| 自最后一次服务端收到上报起 | 在线/事件判定 | 外发通知 |
| --- | --- | --- |
| 未超过 90 秒 | 原规则 | 不发送 |
| 超过 90 秒、未满 180 秒 | 原规则判离线，巡检创建 firing 事件并保留审计 | 不创建失联投递 |
| 达到 180 秒且仍未恢复 | 保持原事件，不改 firing_at | 下一次巡检创建一次失联投递 |
| 发出通知前已恢复 | 事件如实 resolved | 不发失联，也不单独发恢复 |
| 已尝试发送失联后恢复 | 事件如实 resolved | 对已尝试渠道生成/保留恢复投递 |

180 秒从最后服务端上报时间算起，不是从 90 秒报警后再等 180 秒。默认巡检 30 秒，通常在上报空窗约 180–210 秒时进入发送流程；调度、排队、网络和重试仍可能增加延迟，不承诺精确第 180 秒送达。进程启动时原有 90 秒巡检宽限期不变。

独立配置 `AGENT_OFFLINE_NOTIFICATION_AFTER_SECONDS=180` 已加入 Settings、开发/生产 Compose 和配置示例。实际门限取 `max(离线阈值, 通知阈值)`，防止配置成先发通知后判离线。`AGENT_OFFLINE_AFTER_SECONDS=90`、上报间隔、巡检间隔和 Operation 观测新鲜度未修改；未写任何真实 `.env` 文件。

## 实现与并发边界

- `alerts.py`：90 秒创建事件时不提前创建通知；利用持久化 `notification_sequence=0` 表示尚未生成投递，后续扫描达到门限才生成一次，不依赖进程内计时器。未达到门限就恢复的事件保留，但不生成恢复通知。已确认事件不启动延迟首次通知，静默到期继续沿用原重发语义。
- `maintenance.py`：仍按原 90 秒阈值选取/锁定离线 Agent，仅向告警计算传递独立通知阈值。
- `notifications.py`：实际领取投递时锁定对应事件，与恢复的事件行锁协调。已经恢复的旧 firing 不再发送/重试；恢复只对同事件、同渠道存在失联尝试的投递放行，避免多渠道中只收到恢复消息。旧版本已排队的 Agent firing 也重新检查 180 秒门限。
- 未尝试即恢复的排队消息标为终态 `suppressed`，不消耗发送尝试，不清除已有错误/次数。复用现有字符串状态列，无新表或迁移。服务告警的发送/重试不受这些 Agent 条件影响。
- 领取并持久化 `sending/attempt_count` 后会释放数据库事务，再进行网络请求。此时可能已经或即将到达外部服务，无法安全撤回；即使超时仍允许后续恢复通知。应用不能保证外部渠道 exactly-once，既有重试策略未整体重写。

## 后续上线与限制

新版本默认启用 180 秒通知阈值，不需要为此修改原 90 秒离线参数；实际部署仍需单独授权与镜像/CI 验证。上线后应观察短时告警减少、长中断仍能通知，以及各渠道恢复配对；本地测试不替代生产结果。

本片没有修复网络链路，也没有改变通知模板、添加全局摘要或实现恢复稳定窗口。回退到不理解防抖的旧版本时，旧恢复路径可能对尚未生成通知的事件发送孤立恢复消息，应将回退期间通知差异列入观察。
