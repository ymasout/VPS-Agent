固定统计窗口为北京时间 **2026-09-26 23:13:26 至 2026-09-29 23:13:26**（UTC 2026-09-26 15:13:26 至 2026-09-29 15:13:26）。以下时间除特别说明外均为北京时间。查询结束时的在线状态不属于冻结窗口历史。

## 结论

这不是单一的“心跳过于频繁”问题，而是三种情况叠加：

1. 部分上报间隔略超 90 秒，触发告警后很快恢复。
2. 9 月 29 日下午发生真实的、持续约 25 分钟的上报中断，涉及 DMIT 与 Hermes，并伴随其他机器短时异常和控制平面向钉钉投递超时。
3. 恢复通知沿用原事件标题“Agent 失联”或“服务异常”，容易被误认为新故障；部分通知又确实发生了投递重试。

当前证据更支持部分外部通信链路/传输异常，而非整个控制平面停机或资源耗尽。尚不能确定故障发生在运营商、路由、机器网络还是 Agent 客户端；未连接其他 VPS 读取 Agent 日志，不能把推断写成已定位根因。

## 建议，尚未执行

1. **保持约 30 秒上报，不拉长心跳间隔。** 心跳降低频率不能修复集中通信异常。
2. **修正排查前的初步建议：不要直接把全局离线阈值从 90 秒改成 180 秒来降噪。** 代码中的 `agent_offline_after_seconds` 同时用于重启、部署等 Operation 的 `agent_online` 预检（`apps/api/app/operations.py`），不只是通知参数。建议另设独立的通知等待条件，例如上报空窗达到 180 秒才发送失联消息；实际在线状态、事件记录及操作预检仍沿用原规则。按本次已确认的服务端上报空窗估算，11 个 Agent 事件中的 7 个空窗不足 180 秒，有望不再外发通知；另外 4 个仍应保留告警。恢复通知应与已外发/投递结果不确定的失联通知正确配对，避免只收到恢复消息。该方案尚未实现，估算不是上线后的验证结果，也不保证未来降噪比例。
3. 长中断和投递超时应继续作为网络问题排查，不能用更长阈值掩盖。下一份最有价值证据是 DMIT/Hermes 在 09-29 15:00–16:00 的 Agent 日志与对应机房网络事件，需要明确连接目标和访问权限。
4. 后续以单独实现切片改进通知：标题明确区分告警/恢复，展示同一事件编号、上报空窗/持续时长；为抖动设置通知层稳定窗口/合并；评估超时后的不确定投递与重试策略。不得承诺仅靠本地去重就实现钉钉 exactly-once，也不应直接禁用重试而造成真正告警漏报。
5. 通知降噪不得篡改 Agent 实际在线状态、事件审计、Operation 观测新鲜度或健康验证规则。
