## 3. 总体顺序

1. **M7：Web UI 2.0。** 先重建信息架构、视觉系统和核心工作区，保留现有鉴权、审批、状态机和 fail-closed 边界。
2. **M8：结构化运维能力。** 优先扩展固定参数、可预检、可审批、可验证、可审计的操作，减少进入自由终端的必要性。
3. **M9：Web SSH 与限时终端。** 仅作为结构化能力无法覆盖时的最后手段；先做威胁模型和会话授权协议，再考虑界面与实现。

这三个章节按风险递进。M7 可以为 M8 预留展示和交互容器，但不得提前伪造尚不存在的能力；M8 不得借“结构化操作”绕过 M4 的安全闭环；M9 不得把模型或浏览器变成永久 Root 通道。

## 4. M7：Web UI 2.0

### M7.0：现状审计与设计冻结

第一步只做审计、真实使用路径梳理和设计，不直接大面积改页面：

- 盘点桌面端与移动端的导航、页面、数据源、加载/空/错误状态、权限状态和重复组件。
- 用现有生产能力梳理五条主路径：发现异常、查看证据、会话诊断、制定安全操作、独立审批并跟踪验证。
- 明确对话 Provider 的生产运行模式：
  - 若继续使用 deterministic，界面必须如实标明能力边界，不包装成真实模型推理；
  - 若启用真实 Provider，复用严格 `http_json` 边界，并先冻结隐私、成本、限流、超时、输出 schema、引用校验、可用性与回退策略，再做受控金丝雀。
- 冻结设计系统：布局、间距、字体、状态色、表格、筛选、时间线、卡片、表单、确认、通知、移动适配与无障碍基线。
- 输出页面清单、信息架构、组件清单、API/数据缺口和分片迁移顺序；不以静态视觉稿替代真实状态设计。

M7.0 评审通过后的实施分片以 [M7 Web UI 2.0 设计基线 §14](./M7_WEB_UI_2_DESIGN.md#14-实施分片) 为唯一细化基线：

1. **M7.1a 基础设施**：设计 token、基础组件、AppShell、新导航与旧深链兼容；先承载现有内容，不改业务行为。
2. **M7.1b 总览**：按 [冻结视觉基线](./assets/m7/overview-visual-baseline.png) 实现 KPI、需要关注、Fleet 健康、事件状态、进行中 Operation、近期活动与系统信任摘要；Fleet CPU/内存/磁盘增加 Recharts 24h sparkline 和有界历史指标契约。
3. **M7.2a Fleet、机器与服务**：列表/详情分区、跨机器服务清单和逐项失败关闭的批量服务映射复核。
4. **M7.2b 事件与 Agent 对话**：交付一级 Agent 对话工作区，统一 Fleet/机器/服务/事件/仓库上下文、证据区、结构化回答、Provider 透明标签和建议到计划的安全交接；进入本片前冻结空会话模式字段的向后兼容契约。
5. **M7.3 Operation 工作区**：列表、通用展示模型、状态语义、未知类型安全降级；进入本片前冻结候选层 `docker_compose_rollback` 与持久化层 `docker_compose_deploy + rollback_of` 的归一化映射。

## 5. M8：结构化运维能力

建议按以下顺序拆成独立纵向切片，而不是一次性扩成通用命令执行器：

1. **安全 systemd restart**：固定 unit 候选、Agent/控制平面双重 allowlist、状态与健康验证。
2. **自动诊断调度**：只读优先；明确触发条件、频率、去重/幂等、并发、证据预算、Provider 成本、失败退避、审计和人工暂停。不得把每次事件或心跳无界放大成模型调用。
3. **Fleet 分批 Agent 升级**：签名制品、兼容矩阵、分组/暂停、last-known-good 和逐批健康门。
4. **受限清理**：只允许服务端定义的资源类型和范围，先 dry-run，显示可回收量、排除项和不可逆风险。
5. **GitHub 写入**：优先生成分支/PR，不直接写默认分支；仓库 allowlist、最小权限、diff 审查和外部审计齐全。
6. **源码拉取与构建**：最后处理，固定仓库、ref、构建定义、制品身份和部署验证，不接受任意 Shell 片段。

所有写操作继续复用统一闭环：`plan -> precheck -> independent confirm -> signed/expiring/idempotent task -> execute -> verify -> audit`。每个切片都需要独立威胁模型、失败关闭测试、真实隔离验证和单独授权的生产金丝雀。

## 6. M9：Web SSH 与限时终端

Web SSH 工作量不应按“嵌一个终端组件”估算。最小安全范围至少包括：

- 浏览器不持有长期主机私钥；控制平面签发短时、单机、单 Principal、单用途的会话授权；
- Agent 保持主动出站连接，不新增公网 SSH 暴露；会话建立、续期、撤销、超时和断线语义明确；
- PTY 尺寸、输入输出流、背压、心跳、重连、并发限制和资源上限；
- maker-checker、强制原因、显式风险提示、最短权限、自动过期和紧急撤销；
- 元数据审计与敏感输出处理边界。若录屏/记录命令输出，必须先解决秘密、个人数据、容量和访问权限问题；
- 模型默认不能获得终端控制权。未来若允许辅助，只能在新的独立授权与逐步确认协议下设计。

先完成威胁模型、协议和隔离原型，再决定是否进入产品实现。M9 不阻断 M7/M8。
